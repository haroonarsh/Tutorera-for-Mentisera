# TUTORERA Cloudflare MongoDB compatibility spike

This isolated Worker does **not** serve TUTORERA application traffic. Never configure the production API hostname for this project.

## Install and check

```sh
cd cloudflare-api-spike
npm install
npm run typecheck
npx wrangler deploy --dry-run
```

Review the dependency lockfile generated by `npm install` and commit it before enabling CI with `npm ci`.

## Staging setup (authorized operator only)

1. Create a **separate least-privilege MongoDB database user** with only the permissions needed for `ping`. Do not use production administrator credentials.
2. Configure Atlas network connectivity for Cloudflare's outbound environment using the provider's supported secure access method. Avoid opening the production database to all addresses merely for this experiment.
3. Set the Worker secret using `npx wrangler secret put MONGO_URI` (never commit it).
4. Deploy only to the isolated `tutorera-api-compat-spike` workers.dev hostname using `npm run deploy:staging`.
5. Call `/health/live` and `/health/ready` and capture status codes. A 503 readiness result means MongoDB connectivity has not been proven.
6. Review Cloudflare logs without exposing credentials. Test repeated calls, concurrent requests, cold starts and regional latency.

## Security and limitations

- Readiness is publicly callable in this spike and creates a new MongoDB connection per request. **Do not use it for production health checks**; protect/rate-limit or replace it before any broader exposure.
- A successful ping establishes only basic driver connectivity. It does not establish Mongoose compatibility, transaction support, performance, connection-pooling behavior, Socket.IO, payments, file uploads or background jobs.
- No production DNS or frontend API configuration changes are part of this spike.
- Remove the staging Worker and revoke the test credential after testing.
